# UNH Genesis: First-Time GitHub, Ubuntu Setup, Fork, Clone, Run and Contribute Guide

**Audience:** New Genesis collaborators with little or no Git/GitHub experience.
- **Platform:** Each person's **own Ubuntu or Ubuntu/WSL user account**. Use that account for every Git, Conda, test and source-edit command.
- **Canonical source:** https://github.com/utsav-sth/UNH-Genesis-Control
- **Canonical branch:** `main` (use the current approved release, not an arbitrary unvalidated feature branch).
- **Live hardware operations:** Follow [`GENESIS_PANOPTICON_OPERATOR_RUNBOOK.md`](GENESIS_PANOPTICON_OPERATOR_RUNBOOK.md) **only after explicit lab authorization and account-specific commissioning**.

**Last reviewed:** November 4, 2026. **Source baseline checked:** GitHub `main` at `be31172`. This guide does not grant hardware-control authorization.

> [!IMPORTANT]
> **Three different things:** (1) GitHub account = your login on github.com; (2) **fork** = your own repository hosted on GitHub; (3) **clone** = a working copy on your Ubuntu computer. Your Ubuntu username and GitHub username can be different. **Pushing to your fork does not change `utsav-sth/UNH-Genesis-Control`**. A change reaches the original project only if its maintainers intentionally accept it (for example, through a pull request).
>
> **A fork is not a hardware sandbox.** Two Ubuntu users running the same forked software against the same physical instruments can conflict even though their Git repositories are independent. Never run an additional physical IOC, RF output, robot, Magnet or device owner just because a clone is available. Development and testing can be done independently; physical control requires an explicit operator handoff and valid instrument permissions.

## What you will accomplish

1. Create and secure a free GitHub account.
2. Verify shared Git and GitHub CLI (`gh`) tools without sudo.
3. Configure your Git name/email and authenticate *your own* Ubuntu account.
4. Fork Genesis into **your GitHub account**, then clone your fork into **your Ubuntu home directory**.
5. Verify that Git's `origin` is *your fork* and `upstream` is the original project.
6. Install a separate Python/Conda environment, run safe checks and tests, and learn where the operator runbook begins.
7. Work on a personal feature branch, review, commit and push your changes to your fork only.
8. Update your fork from the canonical `main` and deal with common errors.

**Legend:** `✅ ROUTINE` = normal onboarding/Git operation; `🔎 CHECK` = read-only verification; `⚠️ LAB-ONLY` = approval and hardware-specific prerequisites; `🛠️ RECOVERY` = troubleshooting. **Only copy commands from the `bash` blocks** into your Ubuntu terminal. Text outside code blocks is explanation, not a command. Follow the steps in order, and **stop after any `[STOP]` or failed command**. Names in `YOUR_NAME` form are placeholders unless explicitly generated by commands.

## Part A: First-time account and Git setup (do once)

### 1. Create your GitHub account (GitHub website)

1. Visit **https://github.com/signup** and follow the instructions.
2. Select your own unique GitHub username (example: `new-collaborator`).
3. Verify your email address and configure two-factor authentication (2FA).
4. Sign in to GitHub. **Do not use another lab member's GitHub account or credentials.**
5. Keep your GitHub username handy; it may differ from your Ubuntu login name.

GitHub account instructions: https://docs.github.com/en/account-and-profile/how-tos/account-management/creating-an-account-on-github

### 2. Open Ubuntu as yourself

Use your own Ubuntu/WSL login (not `utsav`, `sliferlab`, or another person's account). If you normally SSH into a shared machine, connect with the SSH account assigned to you. The example below is **not** a connection command and does not need root access.

**🔎 CHECK:**

```bash
whoami
printf 'HOME=%s\n' "$HOME"
pwd
ls -ld "$HOME"
```

The home directory should belong to your Ubuntu user, usually `/home/<your-ubuntu-user>`. All new files below go into `$HOME`, not `/home/utsav/...`. If you do not have an Ubuntu account, ask the administrator. Sudo privileges are not required for normal Git operations; do not modify other users' homes.

### 3. Verify shared Ubuntu tools (no sudo required)

**All Ubuntu users can follow normal Git, Conda and source-development instructions without sudo privileges.**

On the shared Genesis Ubuntu machine, the administrator has already
installed Git, GitHub CLI, GNU Screen, curl and wget system-wide.
As of November 3, 2026, all nine existing Ubuntu accounts were checked successfully. Future accounts can normally use the same system-wide tools.

**✅ ROUTINE — Run these checks in your own Ubuntu account:**

```bash
whoami
git --version
gh --version | head -1
screen --version | head -1
curl --version | head -1
wget --version | head -1
```

If these commands succeed, continue to Section 4.

**If a tool is missing:** Contact the Ubuntu administrator.
Only the administrator needs to install shared system packages.
Standard users do not need sudo privileges.

Never use sudo for Git clone, commit, push or personal Conda setup. Do not copy another user's GitHub tokens, SSH keys or Conda directories.
Each user must configure their own GitHub credentials and Git identity.

### 4. Configure your personal Git identity

Your Git commit identity is separate from your Ubuntu login. Use your **own** name and a verified email registered in GitHub **Settings → Emails**. For privacy, you may use the no-reply email GitHub shows there. Do not copy the example placeholders literally.

**✅ ROUTINE — enter your details when prompted (no sudo):**

```bash
read -r -p 'Your name for Git commits: ' GIT_NAME
read -r -p 'Your verified GitHub email (or no-reply email): ' GIT_EMAIL
if [ -n "$GIT_NAME" ] && [[ "$GIT_EMAIL" == *@*.* ]]; then
  git config --global user.name "$GIT_NAME"
  git config --global user.email "$GIT_EMAIL"
  git config --global init.defaultBranch main
  echo '[PASS] Personal Git identity configured.'
else
  echo '[STOP] Please provide your own name and a valid-looking email.'
fi
```

**🔎 CHECK:**

```bash
git config --global --get user.name
git config --global --get user.email
```

If the printed information is wrong, rerun the setup. GitHub only associates commits with your profile when the commit email belongs to your GitHub account.

### 5. Sign your Ubuntu account in to GitHub (recommended: GitHub CLI over HTTPS)

**✅ ROUTINE:**

```bash
gh auth login --hostname github.com --git-protocol https
```

At the prompts, choose **Login with a web browser**, and say **Yes** if asked to authenticate Git using your GitHub credentials. On a remote Ubuntu SSH terminal, use the one-time code and GitHub URL displayed in the terminal **in your local browser**; the browser does not need to run inside Ubuntu. If needed, run `gh auth setup-git` after login to enable Git credential handling.

**✅ ROUTINE / 🔎 CHECK:**

```bash
gh auth setup-git
gh auth status
gh api user --jq .login
```

The final command must print **your GitHub username**. Do not share authentication codes, passwords, credentials or tokens with other users. GitHub does not accept your normal website password for HTTPS Git pushes. With `gh`, a separate personal-access-token setup is not needed.

**Shared-machine credential safety:** `gh` normally uses a secure credential store, but on a headless Ubuntu session it may save a token in `~/.config/gh/hosts.yml`. **Never print that file's contents.** If it exists, secure permissions on your own files:

```bash
if [ -d "$HOME/.config/gh" ]; then chmod 700 "$HOME/.config/gh"; fi
if [ -f "$HOME/.config/gh/hosts.yml" ]; then chmod 600 "$HOME/.config/gh/hosts.yml"; fi
```

Do not sign in while using a shared operator account or another person's Ubuntu login.

**Alternative for advanced users:** SSH keys can be used instead of HTTPS; see https://docs.github.com/en/authentication/connecting-to-github-with-ssh . Keep **private** keys private; only the `.pub` file belongs in GitHub's SSH key settings. Do not mix SSH- and HTTPS-specific setup steps without deciding on one approach.

## Part B: Fork and clone your personal Genesis repository (do once)

### 6. Fork the original Genesis repository (GitHub website)

1. While signed in, visit **https://github.com/utsav-sth/UNH-Genesis-Control**.
2. Select **Fork** near the top-right of the repository page.
3. For **Owner**, choose **your own GitHub account**.
4. Keep the repository name **`UNH-Genesis-Control`** for these instructions.
5. If GitHub offers **Copy the default branch only**, leave it selected for a simple new-user fork. The current default is `main`. Other branches are not required and remain in the original project.
6. Select **Create fork**.
7. Confirm the page URL is `https://github.com/YOUR_GITHUB_USERNAME/UNH-Genesis-Control`, not `https://github.com/utsav-sth/UNH-Genesis-Control`.

GitHub's official forking walkthrough: https://docs.github.com/en/pull-requests/how-tos/work-with-forks/fork-a-repo

> The public project's fork will normally be public as well. **Do not commit secrets, private laboratory data, login details, instrument passwords or SSH keys.** If you need a private development space, ask the project owner about the approved collaboration model before copying controlled material.

### 7. Clone **your fork**, not the original, into Ubuntu

Back in **your own Ubuntu terminal**, verify that `gh auth status` shows your personal account. The next block obtains your GitHub username automatically and refuses to overwrite an existing clone. **It also checks that your repository is actually a fork.**

**✅ ROUTINE — copy the entire block:**

```bash
cd "$HOME"
GH_USER="$(gh api user --jq .login)" || GH_USER=""
echo "Your GitHub username: ${GH_USER:-NOT AUTHENTICATED}"

if [ -z "$GH_USER" ]; then
  echo '[STOP] Sign in with gh auth login before cloning.'
elif [ -e "$HOME/UNH-Genesis-Control" ]; then
  echo '[STOP] ~/UNH-Genesis-Control already exists. Do not overwrite it.'
elif ! gh api "repos/$GH_USER/UNH-Genesis-Control" --jq .fork | grep -qx true; then
  echo '[STOP] Your GitHub fork is missing. Complete Step 6 first.'
else
  git clone "https://github.com/${GH_USER}/UNH-Genesis-Control.git" "$HOME/UNH-Genesis-Control"
fi
```

**🔎 CHECK — only after a successful clone:**

```bash
cd "$HOME/UNH-Genesis-Control"
pwd
git branch --show-current
git log -1 --oneline
git status --short
git remote -v
```

Expected: your own `$HOME/UNH-Genesis-Control`; branch `main`; an empty `git status --short`; and `origin` pointing to **your fork**, not `utsav-sth`. If the folder already exists, ask for help reviewing it rather than deleting or recloning it. If a command fails, **stop rather than continuing with the next numbered step**.

A failed check should not log you out of SSH: unlike an `exit 1` command pasted directly at a shell prompt, the guarded block above just displays `[STOP]`.

### 8. Identify the two GitHub remotes: `origin` and `upstream`

- `origin` = **your GitHub fork**. This is the only remote you push to.
- `upstream` = **the original Genesis repository**. Fetch updates from it; **never** push to it.

**✅ ROUTINE — run after Step 7 succeeds:**

```bash
cd "$HOME/UNH-Genesis-Control"
CANONICAL='https://github.com/utsav-sth/UNH-Genesis-Control.git'
if git remote get-url upstream >/dev/null 2>&1; then
  if [ "$(git remote get-url upstream)" = "$CANONICAL" ]; then
    echo '[PASS] Correct upstream already exists.'
  else
    echo '[STOP] Existing upstream points elsewhere. Ask for review.'
  fi
else
  git remote add upstream "$CANONICAL"
fi

# Conservative defaults for THIS clone, not for other users:
git config --local remote.pushDefault origin
git config --local push.default simple
```

**🔎 CHECK — verify both URLs:**

```bash
git remote -v
git config --local --get remote.pushDefault
```

Expected structure (replace `YOUR_GITHUB_USERNAME` with **your** username):

```text
origin    https://github.com/YOUR_GITHUB_USERNAME/UNH-Genesis-Control.git (fetch)
origin    https://github.com/YOUR_GITHUB_USERNAME/UNH-Genesis-Control.git (push)
upstream  https://github.com/utsav-sth/UNH-Genesis-Control.git (fetch)
upstream  https://github.com/utsav-sth/UNH-Genesis-Control.git (push)
```

Git displays a push URL for `upstream` even if you have no write access. **Do not use it.** Check `git remote get-url --push origin` before each push. A GitHub fork isolates source changes, but users with write permission to the original repository could still affect it if they deliberately push to `upstream`.

## Part C: Install Genesis in your OWN Ubuntu account

### 9. Check the required project and external software

A Git clone provides the **source code**, not the installed lab runtime. The current repo contains `environment.yml`, `requirements.txt`, `requirements-dev.txt`, the `scripts/` launchers and the `docs/` manuals. Additional **Phoebus**, **PyNMR**, lab network, serial/USB access and hardware credentials are not automatically supplied by Git.

**🔎 CHECK:**

```bash
cd "$HOME/UNH-Genesis-Control"
ls -l environment.yml requirements.txt requirements-dev.txt scripts/genesisctl.sh
command -v conda || echo '[INFO] Conda is not installed or not initialized'
command -v phoebus || echo '[INFO] Phoebus is not in PATH'
test -x /usr/local/bin/phoebus && echo '[INFO] System Phoebus launcher present'
```

If Conda is already installed **in your user account**, use that installation and skip Step 10. Do not assume `/home/utsav/miniconda3` or anyone else's Conda setup is usable.

### 10. Install Conda if needed (Miniforge, per-user; no sudo)

If Conda is **already installed for your Ubuntu user**, skip the installer. Verify it with `conda --version` and `conda info --base`. Do not install over an existing Conda directory or use somebody else's private installation.

This documented installer is **pinned to a single verified official Miniforge release**, so the download and its SHA256 are for **the same version**. It is intended for **Linux x86_64** on the Genesis Ubuntu/WSL machine. ARM64 users must consult the official [Miniforge releases](https://github.com/conda-forge/miniforge/releases) for the matching installer and checksum instead of running this example.

**🔎 CHECK:**

```bash
uname -s
uname -m
command -v conda || echo '[INFO] Conda not initialized or not installed.'
```

Expected for this installer: `Linux` and `x86_64`.

**✅ ROUTINE — ONLY if Conda is not already installed:**

```bash
cd "$HOME"
VERSION='26.9.4-1'
INSTALLER="Miniforge3-${VERSION}-Linux-x86_64.sh"
URL="https://github.com/conda-forge/miniforge/releases/download/${VERSION}/${INSTALLER}"
# Official GitHub release asset SHA256 for Miniforge3 26.9.4-1 Linux x86_64.
EXPECTED_SHA256='571b410272cc434f28bc6c5c49ca8ffd4a4d1bcba9f57f1b6baccdb46446cfcc'

if [ "$(uname -s)" != Linux ] || [ "$(uname -m)" != x86_64 ]; then
  echo '[STOP] This installer is only for Linux x86_64.'
elif command -v conda >/dev/null 2>&1 || [ -e "$HOME/miniforge3" ]; then
  echo '[STOP] Conda or ~/miniforge3 already exists. Inspect it; do not overwrite.'
elif curl --fail --location --show-error --retry 3 --output "$INSTALLER" "$URL" &&
     printf '%s  %s\n' "$EXPECTED_SHA256" "$INSTALLER" | sha256sum --check; then
  echo '[PASS] Exact official installer checksum verified.'
  bash "$INSTALLER"
else
  echo '[STOP] Download failed or SHA256 mismatch. Installer NOT executed.'
fi
```

The expected SHA256 above was checked against the **official** [Miniforge release 26.9.4-1](https://github.com/conda-forge/miniforge/releases/tag/26.9.4-1). This removes the unreliable `latest/...sha256` URL that caused problems in the original guide. **Never substitute a `latest` download or change the version without checking and updating its SHA256 as a matching pair.** If the download fails, show the output to the administrator rather than bypassing the checksum.

Follow Miniforge's installation prompts, choose your own home-directory location (normally `$HOME/miniforge3`), and allow Bash initialization. After installation, **open a new Ubuntu terminal** or run:

```bash
source "$HOME/miniforge3/etc/profile.d/conda.sh"
conda --version
conda info --base
```

The base path should be in **your own home directory**. You can leave the base environment inactive until the next step; Genesis uses a separate `genesis-p1` environment. No sudo is needed.

## Part D: Edit, test, commit and push changes to **your fork only**

### 14. Understand `main` versus your feature branch

- `main` tracks the baseline copied from Genesis. Keep it clean and synced; do not develop untested hardware changes there.
- `feature/...` is your personal branch for editing and testing.
- `git commit` saves locally; `git push origin BRANCH` publishes to **your fork** (provided `origin` is still correct).

**✅ ROUTINE — create a new branch BEFORE editing:**

```bash
cd "$HOME/UNH-Genesis-Control"
if [ -n "$(git status --porcelain)" ]; then
  echo '[STOP] Uncommitted changes present. Review them before switching branches.'
else
  git switch main && git switch -c feature/my-first-change
fi
```

Replace `my-first-change` with a meaningful name such as `feature/flowmeter-docs`. Use that **same branch name** in later commands. Do not create/switch branches during any live hardware run.

**🔎 CHECK:**

```bash
git branch --show-current
git remote -v
```

Expected: your personal feature branch; `origin` points to **your fork**. If the branch already exists, use `git switch feature/my-first-change` rather than deleting it.

### 15. Make a small change and inspect it

Open a file in your preferred editor (`nano`, VS Code Remote SSH, etc.). Start with documentation if you are learning Git. For example:

```bash
nano README.md
```

With `nano`, edit, then press **Ctrl+O**, **Enter** to save; **Ctrl+X** to exit. Do not edit tracked device-control or physical safety settings during an active run.

**🔎 CHECK:**

```bash
git status --short
git diff -- README.md
git diff --check
```

`M README.md` means the file has changed locally. `git diff` shows edits that are **not yet staged**. `git diff --check` catches trailing-whitespace problems. If you changed Python code, add/update relevant tests and run them **offline** before proposing any hardware validation:

```bash
conda activate genesis-p1
python -m pytest -q
```

### 16. Stage and commit only the intended files

**✅ ROUTINE — example for a change to `README.md`:**

```bash
cd "$HOME/UNH-Genesis-Control"
git add README.md
git diff --cached --name-only
git diff --cached --stat
git diff --cached -- README.md

if git diff --cached --check; then
  git commit -m "Document beginner setup clarification"
else
  echo '[STOP] Fix the staged whitespace errors before committing.'
fi
```

**🔎 CHECK:**

```bash
git status --short
git log -2 --oneline
```

`git add README.md` is an example: stage **only the file(s) you actually changed**, one at a time. Before committing, inspect the staged file list for archives, passwords, `.env`, SSH keys, GitHub tokens, private data, instrument credentials or runtime logs. Never stage those files. If you see `nothing to commit`, check `git status` and your editor instead of creating a dummy commit.

### 17. Push your feature branch to your own fork

**🔎 CHECK and ✅ ROUTINE — explicitly verify the destination before pushing:**

```bash
cd "$HOME/UNH-Genesis-Control"
GH_USER="$(gh api user --jq .login)" || GH_USER=""
EXPECTED_ORIGIN="https://github.com/${GH_USER}/UNH-Genesis-Control.git"
ACTUAL_ORIGIN="$(git remote get-url --push origin 2>/dev/null)"
BRANCH="$(git branch --show-current)"

printf 'GitHub user: %s\nBranch: %s\nPush URL: %s\n' "$GH_USER" "$BRANCH" "$ACTUAL_ORIGIN"
if [ -z "$GH_USER" ] || [ "$ACTUAL_ORIGIN" != "$EXPECTED_ORIGIN" ]; then
  echo '[STOP] Origin is not your authenticated GitHub fork. Do not push.'
elif [ "$BRANCH" != 'feature/my-first-change' ]; then
  echo '[STOP] You are not on the expected feature branch. Check your branch name.'
elif [ -n "$(git status --porcelain)" ]; then
  echo '[STOP] Uncommitted changes remain. Review/commit them first.'
else
  git push -u origin "$BRANCH"
fi
```

If you chose a different branch name in Step 14, change `'feature/my-first-change'` in the check to your **actual intended branch**. Never change the expected `origin` owner to `utsav-sth` for personal development.

After a successful push, open `https://github.com/YOUR_GITHUB_USERNAME/UNH-Genesis-Control` and select your feature branch to see your commit.

**For later updates to the same feature branch:** switch to your feature branch, edit/test and commit as in Steps 15–16, then **repeat the complete guarded push block above**. Do not use an unverified remote or push to `upstream`.

Do not open a pull request against `utsav-sth:main` unless you intentionally want the maintainers to review your contribution. A forked branch stays independent unless somebody with upstream permission deliberately merges or pushes changes.

### 18. Update your fork when the original project changes

**Easiest beginner option (GitHub website):** Open the `main` branch of **your fork**, click **Sync fork**, review the upstream changes and select **Update branch**. If GitHub reports conflicts, **stop and ask for review**. Do not use a force-sync option. Do not sync during a live hardware run.

Once your fork's GitHub `main` is updated, update your **local** `main`:

```bash
cd "$HOME/UNH-Genesis-Control"
if [ -n "$(git status --porcelain)" ]; then
  echo '[STOP] Review uncommitted changes before syncing.'
else
  git switch main && git pull --ff-only origin main
fi
```

**Alternative using Git from Ubuntu** (for a clean personal `main`, with no active hardware run):

```bash
cd "$HOME/UNH-Genesis-Control"
if [ -n "$(git status --porcelain)" ]; then
  echo '[STOP] Review uncommitted changes before syncing.'
elif [ "$(git remote get-url upstream)" != 'https://github.com/utsav-sth/UNH-Genesis-Control.git' ]; then
  echo '[STOP] Unexpected upstream remote.'
else
  git switch main &&
  git fetch upstream &&
  git merge --ff-only upstream/main
fi
```

If the command-line sync succeeds, you may publish your updated `main` to **your fork only** with this guarded block:

```bash
cd "$HOME/UNH-Genesis-Control"
GH_USER="$(gh api user --jq .login)" || GH_USER=""
EXPECTED_ORIGIN="https://github.com/${GH_USER}/UNH-Genesis-Control.git"
if [ -z "$GH_USER" ] || [ "$(git remote get-url --push origin)" != "$EXPECTED_ORIGIN" ]; then
  echo '[STOP] Origin does not match your GitHub fork.'
elif [ "$(git branch --show-current)" != main ] || [ -n "$(git status --porcelain)" ]; then
  echo '[STOP] Expected clean main branch; review your checkout.'
else
  git push origin main
fi
```

The `--ff-only` option intentionally refuses divergent history. If there is a conflict or failure, do not run `reset --hard`, `clean -fd` or `push --force`.

To bring the updated `main` into your feature branch later (when no live hardware run is using the checkout):

```bash
git switch feature/my-first-change
git merge main
```

If Git reports a merge conflict in hardware-control, interlock or IOC configuration code, contact the subsystem owner; do not choose one side blindly.

### 21. Troubleshooting

**"git: command not found"**: Ask the Ubuntu administrator to install Git system-wide. Do not reinstall Git into another person's home.

**"gh: command not found" / authentication failed**: Ask the Ubuntu administrator to verify the shared GitHub CLI installation; rerun `gh auth login` as **your Ubuntu user** and check `gh auth status`. Do not paste access tokens into chat, documents, shell history or Git URLs.

**"Repository not found" or "Not a fork" when cloning**: Check that you actually created a fork, that the fork URL is correct, and `gh api user --jq .login` returns the intended GitHub account. For private/organization repositories, access restrictions may also apply.

**Git asks for GitHub password on `git push`**: Do not type your normal GitHub website password. Run `gh auth login --hostname github.com --git-protocol https` and `gh auth setup-git`; confirm your fork uses an HTTPS remote.

**"Permission denied" / "403" when pushing**: First inspect `git remote -v`. If `origin` points to `utsav-sth`, you cloned the wrong repository or set the wrong remote. Do not request write access to the original just to finish onboarding. Confirm your fork and remote with the project mentor before fixing it.

**"Identity unknown" when committing**: Repeat Step 4 with your own name and email.

**"nothing to commit"**: Check whether you changed/saved a file and staged it; inspect `git status`.

**"branch already exists"**: `git switch feature/my-first-change` to reopen it, or choose a new branch name; don't delete existing work.

**"Your local changes would be overwritten" / merge conflicts**: STOP. Check `git status` and save/review your own edits before attempting to sync. Never blindly use `reset --hard` or `clean` on a lab checkout.

**`conda: command not found`**: Open a new Ubuntu terminal after installing Miniforge or run `source "$HOME/miniforge3/etc/profile.d/conda.sh"` **only if that file exists in your home**. Do not source another user's Conda installation.

**EPICS port already used, ssRF lock busy, access denied or device disconnected**: This is a **hardware/software ownership** issue, not a Git issue. Do **not** kill somebody else's IOC or remove locks. Stop and contact the current Genesis operator. Another user's fork is not another physical device.

**Phoebus/PyNMR cannot start**: Git and pip do not install those external programs automatically. Follow their separate approved installation and commissioning procedures. Do not use the repo's fixed lab IP settings outside the authorized lab environment.
